What lancee is

lancee is a portable operating workspace for freelancers and small business owners. It keeps client work, ideas, lightweight automations, connected tools, invoices, and payments in one calm place. AI is optional and appears only where it removes meaningful effort from an existing workflow.

The application is built with React, TypeScript, Vite, and a small Express backend, persisted to SQLite. Live platform: agents.hygridtech.co.za.

What's real right now

Authentication, workspace membership, MCP grants and service activation, API keys, Idea quick notes, Paystack invoices/payment links, and the n8n bridge are all backed by durable server flows. Projects, the broader visual board, automation execution, and standard Stripe/PayPal connections are still typed in-memory placeholders.

Product vision

The primary reference user is an independent designer who travels frequently and manages many liquor-label and packaging clients. They need to move from a client request to research, concepts, approvals, delivery, and payment without reconstructing context across scattered tools.

lancee is not an enterprise collaboration suite, a corporate system of record, or an agent-centric product. The user's business and work remain the organizing model — AI is an optional capability inside that model.

Audience

  • Primary: independent designers, consultants, makers, and other client-service freelancers; small business owners who personally manage delivery and operations; people working across locations, devices, clients, currencies, and external tools.
  • Secondary: small studios or partnerships needing shared visibility without enterprise administration; solo operators growing from informal workflows into repeatable processes.

Navigation & information architecture

The primary navigation is stable and user-centered. Global search and quick capture span every section, and each record links to related clients, projects, ideas, invoices, connections, and automation runs.

  • Home — today's priorities, upcoming deadlines, recent activity, blocked work, unpaid invoices, and failed automations. Cards link to their source records; Home is never a separate data silo.
  • Work — clients, projects, briefs, tasks, milestones, files, approvals, and deliverables. Default hierarchy is Client → Project → Work items, with lightweight work allowed before a client is assigned.
  • Ideas — fast capture for notes, references, images, links, and early concepts. Ideas can be tagged, grouped, linked to clients/projects, or promoted into a brief, task, or project while retaining provenance.
  • Automations — user-visible recipes, triggers, runs, approvals, and failure history, described in plain language. Advanced configuration may expose n8n details without making n8n the primary interface.
  • Connections — external services, credentials, permission scopes, sync health, last successful sync, and reconnect controls.
  • Money — estimates, invoices, payment links, payment status, expenses where supported, and a simple cash overview. Stripe, PayPal, and Paystack are first-class providers, represented with their real capabilities rather than false parity.

AI's role

AI appears only when it removes meaningful effort or helps make sense of existing context — summarizing a brief, extracting tasks from approved notes, drafting client communication, finding related references, or suggesting invoice line items from completed work.

  • No essential workflow depends on model availability.
  • People can dismiss, disable, or avoid AI entry points entirely.
  • Generated content is labeled and editable.
  • Sending messages, changing project state, creating charges, issuing invoices, or running external actions requires explicit confirmation unless a bounded automation was deliberately configured.
  • AI is never the primary navigation, product identity, or default owner of work.

Reference end-to-end workflow

  1. While travelling, a designer captures a photo and note in Ideas after seeing an interesting bottle treatment.
  2. A liquor client sends a packaging brief. The designer creates a project in Work, attaches the brief, and links the captured idea.
  3. AI optionally summarizes constraints and suggests a task list; the designer reviews and accepts only useful items.
  4. The project tracks research, label concepts, regulatory copy, dieline preparation, client review, revisions, and final production files.
  5. An approved automation uses n8n to copy final files to connected storage, notify the client, and record the run against the project. Any failure appears on Home and in Automations.
  6. The designer creates an invoice in Money from approved milestones, selects Stripe, PayPal, or Paystack, verifies amount and recipient, and explicitly sends it.
  7. A verified provider webhook marks the invoice paid. Home clears the outstanding-payment alert, and the project timeline records the event.

The full workflow remains possible manually if AI, n8n, MCP, or a payment connection is unavailable.

Live vs. placeholder states

Every surface in lancee exposes its own data state honestly — this documentation uses the same six-state vocabulary throughout, via the status pills you'll see next to features and routes.

StateMeaning
LiveBacked by persisted user data or a verified provider response, with a last-updated time.
PendingSubmitted but awaiting provider, sync, webhook, or automation completion.
Draft / localSaved by the user but not sent or synchronized.
SampleDemo or onboarding content, visually labeled and removable in one action.
PlaceholderIntentionally unavailable capability; non-interactive unless it opens an explanation or waitlist.
Error / staleFailed or outdated data, with the last successful state preserved and a recovery path.
No fabrication

No fabricated balances, activity, client records, automation success, or payment status may ever appear as live. Prototype actions must never imply an external side effect occurred.

Success metrics & roadmap

Activation, durable use, and business outcomes matter more than raw engagement: time to first client/project, completion rate of brief → delivery → invoice, weekly active owners across two or more core sections, invoice/payment-link send rate, automation success rate, connection/sync health, and four- and twelve-week retention.

1 · Coherent coreSix-section navigation, shared record-linking, Home attention view, basic Money records, explicit sample/live/pending/error states, manual workflows end to end.

Install & run locally

1 · Install the application

cd /home/apps/agent-app
pnpm install --frozen-lockfile

pnpm-lock.yaml is the source of truth — use --frozen-lockfile on servers and in CI so a deployment can't silently change dependency versions.

2 · Create the server environment

test -f .env || cp .env.example .env
chmod 600 .env

At minimum, set:

APP_ENV=production
PORT=5177
PUBLIC_ORIGIN=https://agents.hygridtech.co.za

ADMIN_NAME=Workspace Admin
ADMIN_EMAIL=admin@example.com
ADMIN_PASSWORD_SALT=
ADMIN_PASSWORD_HASH=
SESSION_TTL_HOURS=12
WORKSPACE_ID=wsp_primary
WORKSPACE_NAME=Hookitup Solutions
DATABASE_PATH=.runtime/lancee.sqlite

Use the exact public scheme and hostname for PUBLIC_ORIGIN, with no trailing slash. Then generate administrator credentials interactively:

pnpm auth:hash
Never store the plaintext password

The password is hidden while typing and must be at least 12 characters. Copy the generated ADMIN_PASSWORD_SALT and ADMIN_PASSWORD_HASH into .env — the plaintext password itself must never enter .env, source code, documentation, shell history, or a support message.

.runtime/session-secret and .runtime/lancee.sqlite are created with restrictive permissions on first run — preserve both across restarts. Both .env and .runtime/ are ignored by Git.

3 · Run the complete platform

pnpm build
APP_ENV=development PUBLIC_ORIGIN=http://localhost:5177 pnpm start

Open localhost:5177 — the public landing page should load before authentication. If you browse through a different local hostname or IP, set PUBLIC_ORIGIN to that exact browser origin, including scheme and port.

Frontend-only development

pnpm dev

Vite listens on 0.0.0.0:5177. This does not start Express, so login, SMTP, and MCP endpoints won't work — use the complete workflow above whenever backend behavior matters.

Architecture

Platform layers

The platform is intentionally split into layers so the UI never depends on a specific database or auth vendor:

  1. src/App.tsx owns presentation, navigation, local view state, feedback, and interactions.
  2. src/lib/mockApi.ts owns remaining placeholder contracts and seeded domain data, while routing durable auth, MCP state, and API-key actions to Express.
  3. src/lib/offlineStore.ts and src/lib/ideasRepository.ts own workspace-partitioned IndexedDB snapshots, queued Idea mutations, reconnect sync, and conflict resolution.
  4. server/database.mjs owns the SQLite schema and workspace-scoped durable repositories.

Durable foundation

lancee persists identity, workspace membership, MCP grant state, MCP service activation, API keys, Idea notes, payment state, n8n delivery state, and mutation-idempotency records in SQLite at .runtime/lancee.sqlite.

.runtime/ is Git-ignored and restricted to the server operator. On startup the app enforces mode 0600 on the database and enables foreign-key enforcement, write-ahead logging, full synchronous durability, a five-second busy timeout, and strict SQLite tables.

Idempotent mutations

Durable workspace mutations require an Idempotency-Key header, 8–128 characters. The server scopes the key to the workspace and route, hashes the normalized request, and stores the response for 24 hours.

  • Repeating the same route, key, and payload replays the original response and sets Idempotency-Replayed: true.
  • Reusing the key with a different payload returns 409.
  • Omitting or malforming the key returns 400.
  • API-key creation stores only non-secret response data — its one-time secret is deterministically reconstructed for an idempotent retry from the server signing secret, workspace, key, and creation timestamp.

Authentication & notifications

Session & sign-in flow

lancee uses an application-owned Express session rather than Firebase, keeping authentication, MCP grants, n8n signing secrets, SMTP credentials, and future provider tokens behind one trusted backend. Firebase remains a reasonable future identity provider — its ID token would be verified here and exchanged for the same session model.

  1. The public landing page renders for a visitor with no session.
  2. GET /api/auth/session restores an existing signed session.
  3. POST /api/auth/login resolves the user and owner membership from SQLite, then verifies the configured administrator with scrypt.
  4. The server issues lancee_session as an HttpOnly, Secure, SameSite=Lax cookie.
  5. POST /api/auth/logout expires the cookie, returns to the landing page, and clears the browser's IndexedDB data.
Security defaults
  • 12-hour default session expiry, persistent 384-bit signing secret in .runtime/session-secret.
  • Constant-time password comparison; five failed attempts per IP per 15 minutes.
  • Same-origin checks for mutations; CSP, frame denial, MIME-sniffing protection, referrer policy, restrictive permissions.
  • Cache-Control: no-store on authentication and MCP grant state.

After one authenticated load, the browser retains a non-secret display snapshot of the last user/workspace so the installed shell can reopen cached Idea notes offline. This snapshot is never accepted by the server and never replaces the signed cookie.

Administrator sign-in & password rotation

Open agents.hygridtech.co.za, select Sign in, and use the email in ADMIN_EMAIL with the password used to generate the current hash. There is no dashboard bypass and no plaintext password stored on the server.

pnpm auth:hash

The script prompts without echoing the password and prints a new ADMIN_PASSWORD_SALT / ADMIN_PASSWORD_HASH. Replace both in .env, then reload PM2 with --update-env.

n8n bridge Live & durable

A bidirectional, signed webhook bridge:

lancee -- signed GET/POST --> n8n
lancee <-- signed GET/POST -- n8n

Configuration, nonce use, and every accepted or attempted delivery are durable per workspace.

Server configuration

N8N_BASE_URL=https://n8n.hygridtech.co.za
N8N_SIGNING_SECRET=
N8N_TIMEOUT_MS=10000

N8N_BASE_URL is the only allowed outbound origin. In production: HTTPS is required, embedded credentials/URL fragments are rejected, the origin must exactly match, DNS must resolve only to public addresses, and redirects are rejected. N8N_SIGNING_SECRET is an optional bootstrap secret — the Connections UI can set or rotate a workspace secret, encrypted at rest with AES-256-GCM. N8N_ALLOW_PRIVATE=true exists only for development verification and is ignored in production.

Configure in lancee

  1. Create and activate an n8n workflow with a production Webhook node.
  2. Open Connections → n8n.
  3. Enter a webhook on the configured n8n origin, e.g. https://n8n.hygridtech.co.za/webhook/lancee.
  4. Enter a shared secret of 32–256 characters, then save.
  5. Send real outbound GET and POST deliveries.
  6. Copy the generated inbound callback into the n8n HTTP Request node.

Signature contract

X-Lancee-Timestamp: <Unix milliseconds>
X-Lancee-Nonce: <base64url random value>
X-Lancee-Signature: <HMAC-SHA256 hex>
X-Lancee-Correlation-Id: <stable correlation id>
X-Lancee-Delivery-Id: <delivery id>   # outbound only

The canonical signing value is five newline-separated fields:

timestamp
nonce
UPPERCASE_METHOD
path_and_query
sha256_hex_of_exact_body_bytes
signature = hex(HMAC-SHA256(shared_secret, canonical_value))

For GET, the body is empty and the query string is part of the signed path. Inbound timestamps must be within five minutes of server time; nonces are stored per workspace and accepted once, then retained ten minutes for replay cleanup.

Outbound delivery & retry

Outbound delivery creates a pending record before network I/O, sends with redirects disabled and a bounded timeout, then records succeeded (status + duration) or failed (normalized error code, status, duration). A manual retry creates a new attempt, retains the original correlation ID, links retry_of, and is limited to five attempts.

Money

Paystack payment flow Live

invoice details → Paystack hosted checkout → verified webhook → paid invoice

Uses Paystack's documented server-side secret-key authentication — no assumed OAuth flow, and the secret never enters the browser or SQLite.

Configuration

PAYSTACK_SECRET_KEY=sk_test_replace_me
PAYSTACK_BASE_URL=https://api.paystack.co
PAYSTACK_CALLBACK_URL=https://agents.hygridtech.co.za/?payment=paystack

Start with an sk_test_... key — the Money UI reports test or live mode from the key prefix. lancee stores only a short SHA-256 fingerprint and the fact that the connection comes from the environment. Configure this webhook in the Paystack dashboard:

https://agents.hygridtech.co.za/api/webhooks/paystack

User flow

  1. Open Money and confirm the Paystack card says Connected (test or live).
  2. Select Create payment link and enter client, email, project, ZAR amount, description, and optional due date.
  3. Confirm creation — lancee initializes a hosted checkout but does not email, message, or charge the client automatically.
  4. Review or copy the returned checkout link, then choose how to share it.
  5. A verified charge.success webhook reconciles the invoice as paid.

The current flow intentionally supports ZAR only — multi-currency remains a later roadmap item.

Webhook security & boundaries

MethodRouteAuthentication
GET/api/money/paystack/statusWorkspace session
GET/api/money/invoicesWorkspace session
POST/api/money/paystack/payment-linksSession + Idempotency-Key
POST/api/webhooks/paystackPaystack HMAC signature

The webhook route reads the raw request body before JSON parsing, recomputes x-paystack-signature as HMAC-SHA512 with the server secret, and compares it in constant time. A signed event marks an invoice paid only when:

  • the event type is charge.success;
  • the provider reference matches a known Paystack payment link;
  • provider status is success;
  • amount and currency exactly match the stored values.

Unknown, irrelevant, or mismatched signed events are acknowledged but never change money records; exact duplicates never reprocess. Raw provider payloads are not retained — lancee stores a hash and normalized result. Database triggers reject changes to invoice/payment-link provider references after insertion.

Honest boundaries

Checkout initialization and webhook reconciliation are live when a key is configured. The app creates a hosted link — it never directly charges stored cards, and nothing is sent to a client automatically. Refunds, partial payments, disputes, verification recovery, tax, and multi-currency are not yet implemented. Stripe and PayPal remain labelled previews.

lancee is installable as a PWA and provides a deliberately narrow offline workflow for quick notes on the Ideas canvas.

The cached identity is a display snapshot, not an authentication credential — the signed session remains an HttpOnly cookie. Explicit sign-out clears the cached identity, Idea snapshots, and queued mutations from IndexedDB.

Install behavior

public/manifest.webmanifest defines the standalone identity, colors, scope, and icon. public/sw.js installs only in production and:

  • precaches the HTML shell and hashed CSS/JS assets;
  • uses a network-first navigation strategy with an offline shell fallback;
  • caches same-origin static GET assets;
  • bypasses every /api/ request and every non-GET request;
  • removes previous shell cache versions on activation.

Installation requires HTTPS in production (or localhost in development) and one successful online load before the shell works offline.

Idea notes, queueing & conflicts

MethodRouteContract
GET/api/ideas/notes?boardId=...Authenticated workspace read
POST/api/ideas/notesSession + stable Idempotency-Key
PATCH/api/ideas/notes/:noteIdSession + stable key + expectedVersion

The browser commits the local note and queue record to IndexedDB before trying the network — each mutation retains its body and idempotency key, so a lost response can be retried without creating a duplicate or double-applying an edit.

The queue flushes immediately after a local write when online, on the browser's online event, when an authenticated workspace is restored, or after a supported Background Sync event. HTTP 5xx, network failure, or expired auth leaves the mutation queued; a permanent client rejection is surfaced for review rather than dropped silently.

Conflict handling

Edits send the version they were based on — the server updates only when expectedVersion matches the current row version, otherwise it returns 409 with the current server note. The Ideas canvas then offers an explicit choice:

  • Use server removes the queued mutation and restores the current server version.
  • Keep mine issues a new mutation and idempotency key based on the returned server version.

This is deliberate last-writer resolution — the queue never silently overwrites a newer server note.

Local-data note

IndexedDB data is scoped by workspace but not encrypted by lancee — rely on OS-level device encryption and account lock on shared devices. Don't use the Idea quick-note field for credentials or regulated secrets. Broader visual-board records, attachments, projects, and automations are not yet offline domain records.
